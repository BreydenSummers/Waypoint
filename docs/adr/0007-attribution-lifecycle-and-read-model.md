# ADR-0007: Attribution persistence, actor lifecycle, and authoritative reads

- Status: Accepted
- Scope: v1

## Context

The capture envelope already carries the source-agent, execution, timing, network, parser, target,
and evidence facts required by the PRD. Persisting only a subset makes the accepted write impossible
to reconstruct and lets UI/report projections become accidental sources of truth. The v1 API also
needs an operational actor lifecycle and explicit read models for Recon, Attacks, evidence, reports,
and observed claims. Audit events are an ordered mutation log, not a replacement for authoritative
resource reads.

## Decision

- A successfully accepted capture materializes one immutable action that losslessly retains the
  complete validated capture envelope: source-agent identity/version/platform; command, argv, cwd,
  target, phase, initiation and AI decision context; collector wall-clock timing and duration;
  execution status/exit/signal/failure; exec-host address/method/interface/confidence; egress
  mode/status/address/observation time; ordered pivots; parser state; and distinct evidence
  descriptors. Server receipt time, clock-skew result, credential-derived engagement, and an
  event-time actor snapshot are stored alongside it.
- The authoritative action read returns that lossless capture plus opaque, engagement-scoped evidence
  references. Audit events may remain safe summaries, but cannot be the only way to retrieve action
  facts. Bounded keyset APIs expose actions, entities with observation provenance, evidence metadata
  and bytes, out-of-band claims, actors, and frozen report inputs. Browser and report code must not
  invent or silently fall back to engagement facts.
- Actor provisioning, listing, rotation, and revocation are core lifecycle operations. Tokens are
  actor-specific, generated by the server, returned only in a one-time provisioning/rotation
  response, digest-stored, and never returned by reads or events. Revocation is durable and applies
  to REST, MCP, and new SSE connections. AI actors require a referenced active human authorizer plus
  agent name, model, and version. Lifecycle mutations use the application authorization/audit
  transaction from [ADR-0002](0002-append-only-audit.md).
- Imported entity/result observations enter through a claim service. The server creates the claim ID
  and flags a claim whenever no valid engagement-scoped captured source action can be proved. Pending
  claims remain visibly non-authoritative until an operator links them to an immutable action or
  dismisses them. Both transitions are audited. This is best-effort detection of observations seen
  by Waypoint; wholly unobserved execution remains outside the guarantee.
- Collection and list endpoints derive engagement and actor scope exclusively from the credential.
  All collection reads are bounded and keyset-paginated. Resource lookup returns the same
  non-enumerating not-found result for absent and foreign-scope IDs.

## Consequences

Database migrations and application models must preserve every contracted field rather than keeping
only an action summary. Larger immutable rows are acceptable because raw bytes remain in the evidence
store and list projections stay bounded. Actor/event snapshots preserve historical attribution while
the actor lifecycle resource exposes current revocation state.

The out-of-band queue cannot prove that nothing happened outside Waypoint. Product/report copy must
show known pending/dismissed gaps without upgrading a claim into captured provenance. These read
contracts do not add an analytical graph, guided command surface, or model capability.

## Verification

- Round-trip every valid human/AI capture fixture through PostgreSQL and compare the authoritative
  action projection field-for-field with the accepted envelope and actor/source credential.
- Provision, rotate, revoke, list, and authenticate human/AI actors; prove one-time secrets never
  appear in reads, audit metadata, SSE, or logs and that a non-human AI authorizer is rejected.
- Exercise bounded action/entity/evidence/claim reads under cross-engagement IDs and pagination.
- Submit claims with missing, foreign, and valid source actions; prove only the valid source becomes
  authoritative and every flag/resolution has one actor-attributed event.
